# Supabase Sequences

## Purpose

Capture PostgreSQL sequences currently defined within the CAFLA application schemas.

Sequences may support auto-incrementing identifiers or other database-generated numeric values and can remain as dependencies of current or legacy database objects.

This inventory completes the structural evidence needed for the initial Supabase cleanup audit.

---

## Scope

Schemas included:

- `public`
- `tournaments`
- `development`

Metadata captured:

- Schema
- Sequence name
- Data type
- Start value
- Minimum value
- Maximum value
- Increment

---

## Query

```sql
select
  sequence_schema,
  sequence_name,
  data_type,
  start_value,
  minimum_value,
  maximum_value,
  increment
from information_schema.sequences
where sequence_schema in ('public', 'tournaments', 'development')
order by
  sequence_schema,
  sequence_name;
```

## Result

```json
No rows returned
```

---

## Result Interpretation

Each row represents one PostgreSQL sequence.

Important fields:

- `sequence_schema` — schema containing the sequence.
- `sequence_name` — sequence identifier.
- `data_type` — numeric type generated by the sequence.
- `start_value` — initial sequence value.
- `minimum_value` — minimum allowed value.
- `maximum_value` — maximum allowed value.
- `increment` — amount added for each generated value.

Sequences are commonly associated with:

- `SERIAL`
- `BIGSERIAL`
- Identity-style numeric identifiers
- Explicit calls to `nextval(...)`

CAFLA also uses UUID-based identifiers extensively, so not every table is expected to require a sequence.

---

## Audit Notes

A sequence must not be classified as unused based solely on its name.

Sequence dependencies may be visible through:

- Column defaults.
- Table identity configuration.
- Function definitions.
- Application/database logic.

`04-columns.md` should be cross-referenced for defaults containing expressions such as:

`nextval(...)`

If no rows are returned, that is still a valid audit result and should be recorded as:

```json
[]
```
