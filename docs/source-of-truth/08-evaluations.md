# Evaluations V2

## 1. Purpose and Scope

Evaluations V2 derives directional peer-evaluation obligations from completed
match crews, accepts one evaluation per evaluator/evaluated/match relationship,
and converts on-time received quality plus evaluator compliance into a
Development metric. This document describes the CURRENT implementation at
`develop@f236021`; it does not redesign crew history, participation, privacy,
or scoring.

## 2. Status and Architecture Boundary

- `public.evaluations`: **CURRENT** canonical submitted-evaluation table. Its
  `public` location does not make it legacy.
- `development.referee_evaluation_detail` and
  `development.referee_evaluation_score`: **CURRENT** derived V2 sources.
- Population and historical crew semantics: **TRANSITIONAL** because current
  match assignments and independently repeated cycle-member predicates define
  obligations.
- No separate current Evaluation V1 table/view/helper tree was identified.
  Older peer-feedback/dashboard scoring architecture is **RETIRED**; the
  surviving `dashboard_referee_activity` is CURRENT and only counts received
  evaluation rows.

The repository database baseline is
`supabase/migrations/20260831185011_remote_schema.sql`. Historical evidence in
`docs/audit/supabase/` is point-in-time supporting evidence, not live state.

## 3. Surfaces and Application Implementation

### Member

- `/portal/evaluations`: authenticated list of current-cycle obligations and
  recent obligation activity.
- `/portal/evaluations/[match_id]?referee=[evaluated_id]`: authenticated form or
  closed state for one derived obligation.
- `POST /api/evaluations/submit`: authenticated validation and insert.
- Portal Dashboard: pending cards from `getUserEvaluationObligations()` and
  Peer Feedback score from `getUserEvaluationScore()`.
- `/portal/development`: displays the aggregate Evaluation Score.

### Board

No dedicated Evaluation administration surface was found. Board can see the
aggregate score and received-evaluation count on Admin Member Detail through
`getMemberDashboard()`. Historical RLS permits Board reads and updates of base
rows, but that database capability is not evidence of a current Board workflow.

## 4. Ownership and Data Model

`public.evaluations` owns submitted evidence:

| Column | Meaning |
|---|---|
| `id` | UUID evaluation identity. |
| `match_id` | Nullable FK to `public.matches`; match deletion cascades the row. |
| `evaluator_id` | Nullable FK to `public.members`; submitting referee. |
| `evaluated_id` | Nullable FK to `public.members`; reviewed referee. |
| `role_of_evaluator`, `role_of_evaluated` | Text copied from the derived obligation. |
| Five score columns | Integer category values constrained individually to 1–5 when non-null. |
| `comments` | Optional text with no discovered length constraint. |
| `created_at` | `timestamp without time zone`, default `now()`; used as submission time. |

The exact uniqueness contract is
`UNIQUE(match_id, evaluator_id, evaluated_id)`. Because the three columns are
nullable, PostgreSQL uniqueness does not by itself prohibit multiple rows
containing nulls; the current endpoint always supplies all three.

An **obligation** is not a row in `public.evaluations`. It is dynamically
generated by `development.referee_evaluation_detail`. A submitted row is joined
onto that current obligation key.

## 5. Crew-Derived Obligation Graph

For a three-referee crew, the view creates six directed pairs:

```text
Center -> AR1    Center -> AR2
AR1    -> Center AR1    -> AR2
AR2    -> Center AR2    -> AR1
```

Pairs with a null member or identical evaluator/evaluated ID are removed.
Duplicate assignment IDs can therefore remove self-pairs but can still make
multiple UNION branches describe the same remaining pair; `UNION ALL` does not
deduplicate. The base unique constraint permits only one submitted row per
directional key, while the detail view could display duplicate obligations if
crew slots are malformed.

Obligations are derived from the **current** values of
`center_referee_id`, `assistant_referee_1_id`, and
`assistant_referee_2_id`. Reassignment can remove or create obligations. A
previously submitted evaluation remains in the table but disappears from the
detail/score chain if its pair is no longer generated. Match deletion removes
both the source match and submitted evaluations through cascade.

## 6. Activation Boundary

The CURRENT detail view only considers matches whose timezone-less kickoff
date is on or after `2026-09-18`, with one hard-coded exception:

`cb5cb563-d55d-4c74-a91f-e28b9e486e55`

The date is a technical Evaluations V2 activation boundary embedded in the
baseline view; it is not a scoring-period date. The UUID exception is
**DEVELOPMENT/TEST EVIDENCE** embedded in the current database definition. Its
purpose and suitability in Production require external confirmation; it must
not be generalized into a business rule.

Only past matches inside the active Development cycle enter the view.

## 7. Deadline and Time Semantics

The deadline is exactly `kickoff_at + interval '48 hours'`.
`public.matches.kickoff_at` and `evaluations.created_at` are both timestamp
without time zone, but the view treats them differently:

- kickoff is compared directly with Los Angeles-local `now()`;
- `created_at` is interpreted as UTC and converted to Los Angeles local time;
- deadline is calculated directly from timezone-less kickoff.

Pending lasts through `now() <= deadline`; submission at the exact deadline is
on time. This inherits `MATCH-TIME-001`: correctness near DST or implicit
timezone boundaries is not guaranteed by a single canonical storage contract.

## 8. Submission Flow

```text
current derived obligation
  -> authenticated form
  -> server payload/category validation
  -> re-query authenticated member's obligations
  -> require exact match/evaluated/evaluator and pending state
  -> session-scoped insert into public.evaluations
  -> RLS + unique constraint
  -> derived views update on the next read
```

The evaluator ID and roles come from the authenticated obligation, not the
client payload. Match and evaluated IDs are client inputs but must match that
obligation. Self-evaluation is excluded by the detail view and checked again by
the API. The DB insert policy requires evaluator `auth.uid()` and both parties
to be members of the current match crew, but does not independently forbid
self-evaluation or enforce the deadline.

The API accepts only `pending`; it rejects `missed` with 410 and any completed
state with 409. Therefore CURRENT application behavior does not accept late
submissions, even though the detail model can classify an existing row as
`completed_late`.

## 9. Category and Comment Model

All five categories are required by current UI/API and use integer values 1–5:

- `arrival_score`
- `fitness_score`
- `communication_score`
- `teamwork_score`
- `professionalism_score`

The database range checks apply only to non-null values; it has no NOT NULL
constraints for categories. The API supplies all five. Comments are optional,
trimmed, and stored as null when empty. No category weights were found: all
five contribute equally.

## 10. Obligation State Semantics

States are calculated on every view read; none is stored:

| State | Definition |
|---|---|
| `pending` | No joined evaluation and current LA-local time is at/before deadline. |
| `completed_on_time` | Joined evaluation exists and converted creation time is at/before deadline. |
| `completed_late` | Joined evaluation exists after deadline. |
| `missed` | No joined evaluation and deadline has passed. |

Time alone moves pending to missed. A late row can move missed to
completed_late through a non-current write path. `compliance_point` is 1 only
for completed-on-time, otherwise 0.

## 11. Quality Formula

Per submitted obligation:

```text
quality_percentage =
  round((arrival + fitness + communication + teamwork + professionalism)
        / 25 * 100, 2)
```

Member Quality is the average of `quality_percentage` for evaluations
**received** with status `completed_on_time`, rounded to two decimals. Late
evaluations and missing obligations do not enter Quality. With no on-time
received evaluation, Quality is null rather than zero. Category averages use
the same on-time-only population.

## 12. Compliance Formula

Compliance measures evaluations the member was required to **submit**:

```text
evaluations_due = all obligations except pending
compliance_percentage =
  round(completed_on_time / evaluations_due * 100, 2)
```

Pending obligations are excluded from the denominator. Late and missed are due
but add nothing to the numerator. When nothing is due, compliance is null.

## 13. Evaluation Score and Minimum Evidence

The view implements exactly:

```text
evaluation_score = round(quality_percentage *
                         (compliance_percentage / 100), 2)
```

It is null if either Quality or Compliance is null. Status becomes
`insufficient_feedback`, `compliance_pending`, or `scored` accordingly.

The Evaluation metric itself has no threshold beyond having at least one
on-time received evaluation and at least one due obligation to make both
inputs non-null. Ranking uses a separate minimum: when Evaluation is available,
the monthly ranking chain requires at least one due obligation and at least one
on-time evaluation received. It then applies evidence-normalization benchmarks.
That ranking minimum must not be described as the Evaluation formula itself.

## 14. Population and Participation Boundaries

| Boundary | CURRENT population |
|---|---|
| Ability to submit | Exact pending obligation returned for authenticated evaluator. |
| Obligation generation | Both pair members must have active/withdrawn cycle status, `eligible_for_ranking = true`, and kickoff within each stored effective interval; cycle must be active. |
| Detail inclusion | Same dynamically derived obligation; current crew and current cycle-member rows are re-evaluated. |
| Cycle Evaluation Score | Active/withdrawn and ranking-eligible cycle members only. |
| Monthly Development/Ranking | Independently active/withdrawn, ranking-eligible, and bounded by stored effective dates/period cutoff. |

None of these reads `public.members.status` or branches by `enrollment_type`.
Consequently invited public members with active/eligible cycle rows can create
and receive obligations. Ineligible participants do not receive V2 obligations
at all, conflating Development participation with ranking eligibility. This is
the Evaluations instance of `POP-001`.

## 16. Historical Behavior

Historical evidence is not immutable in the derived layer:

- withdrawal with a correct historical effective end can preserve earlier
  obligations because withdrawn is accepted;
- changing cycle status to `ineligible`, ranking eligibility to false, or
  effective dates can remove all or part of prior obligations/evidence;
- changing public member status alone has no effect;
- changing current crew assignments can remove submitted evidence from detail
  and scoring or create new historical obligations;
- deleting a match cascades submitted rows;
- the base evaluation remains stored after ordinary reassignment, but becomes
  orphaned from this calculation unless the same directed pair remains.

No crew/obligation snapshot table was found. This shares `MATCH-HIST-001` and
creates `EVAL-HIST-001` for evaluation-specific consequences.

## 17. Dashboard and Privacy

The member Dashboard reads pending obligations from
`referee_evaluation_detail` and aggregate score from
`referee_evaluation_score`. It does not show evaluations received, individual
reviewer identities, individual category scores, or comments.

The Evaluations page is evaluator-facing: it shows rows the authenticated
member was expected to submit, including their own submitted scores/comments.
No current evaluated-member review surface was found. Admin Member Detail shows
only aggregate Evaluation Score and `dashboard_referee_activity`'s raw count of
all evaluation rows received. Board-wide base-row visibility exists in RLS,
but no dedicated Board detail UI was found.

Baseline RLS technically allows an evaluated participant to SELECT individual
rows, including evaluator identity, categories, and comments, if they query the
table directly. The current UI does not expose that access. Therefore the
product is not anonymous at the database-policy layer.

## 18. Development and Ranking Dependency

```text
public.matches current crew + development.cycle_members
  -> development.referee_evaluation_detail
     + public.evaluations
  -> development.referee_evaluation_score
  -> development.referee_monthly_period_metric_scores_v2
  -> development.referee_monthly_development_score_v2
  -> development.referee_monthly_ranking_evidence_v2
  -> development.referee_monthly_ranking_history_v2
  -> development.referee_current_ranking_v2
  -> development current/monthly snapshot tables
```

Monthly calculation recomputes Quality and Compliance inside each applicable
period cutoff. Evaluation contributes to Development only when its configured
period weight is positive and its score is non-null. Ranking availability and
minimum/evidence rules are separate downstream decisions.

`dashboard_referee_activity` independently counts every stored evaluation by
`evaluated_id`; unlike V2 Quality it does not require on-time status or a still-
valid derived obligation.

## 19. Authorization and Security

- **EVAL-SEC-001 / CURRENT:** the application insert path is strongly bound to
  the session user and exact derived pending obligation; duplicate concurrency
  is protected by the unique constraint.
- **EVAL-SEC-002 / SHOULD FIX AFTER LIVE VERIFICATION:** baseline
  `evaluations_update_evaluator_only` checks only that `evaluator_id =
  auth.uid()` before and after update. With broad authenticated table grants, a
  direct caller could alter their submitted categories/comments and may change
  match/evaluated IDs without repeating crew, deadline, or immutable-submission
  validation. The current UI/API does not offer updates.
- **EVAL-SEC-003 / CURRENT GAP:** DB insert RLS confirms both users belong to
  the match crew but does not prohibit `evaluated_id = evaluator_id`, enforce
  the V2 activation/deadline/cycle population, require all scores, or validate
  stored role strings. Current endpoint/detail checks cover these for the
  normal route, but direct authenticated inserts may bypass them.
- **EVAL-SEC-004 / PRIVACY DECISION:** participant SELECT RLS gives an evaluated
  member the evaluator identity, scores, and comments. Whether this is intended
  non-anonymous feedback requires owner confirmation.
- Live post-recovery RLS/grants must be verified read-only before remediation.

No DELETE policy was found; broad grants do not make DELETE pass RLS without a
policy. Anonymous grants likewise have no matching permissive policy in the
baseline.

## 20. Transaction and Concurrency

Submission is one database insert after a separate obligation read. Crew,
membership, or time can change between them. RLS rechecks current crew but not
the detail view's deadline/activation/population predicates. The unique
constraint deterministically resolves simultaneous duplicate inserts; the API
maps SQLSTATE `23505` to 409.

Obligation status is not materialized. Successful insertion immediately changes
derived views on subsequent reads. There is no multi-row partial-write risk in
the normal submission itself, but there is a read/insert authorization-time
boundary and no immutable database submission contract.

## 21. Known Gaps and External Verification

- `EVAL-POP-001`: population ignores public status and couples obligations to
  ranking eligibility.
- `EVAL-HIST-001`: mutable current assignments/membership can rewrite derived
  historical obligations and scoring.
- `EVAL-TIME-001`: mixed timezone-less timestamp interpretation affects 48-hour
  status.
- `EVAL-ACT-001`: hard-coded Development/test match exception exists inside the
  current view and needs environment/purpose confirmation.
- `EVAL-SEC-002` through `EVAL-SEC-004`: update/insert/privacy policy behavior
  needs live verification and owner decisions.
- `EVAL-ADMIN-001`: no dedicated Board review/administration UI was found.

External read-only verification should confirm current view definitions, RLS,
grants, policies, row counts, the exception match's environment/purpose, and
whether any external client directly reads or updates `public.evaluations`.
